# Procedural blended cartoon hand in three.js (one seamless surface from primitives, headless SwiftShader)

Context for the report writer: the engine renders in headless Chromium with SwiftShader (`engine/render.mjs` launches with `--use-angle=swiftshader`), uses three.js 0.186.1 (`node_modules/three/package.json`), and draws the "anime" style ink lines with three's `OutlineEffect` (inverted hull, `engine/page/styles.js`). The current glove hand (`engine/page/potato.js` `_mitten`) is built from separate spheres/capsules plus "round knuckle" balls, which is the setup this research is about replacing. Timings marked "local benchmark" were measured in this session on this container (4 vCPU, Node v22.22.0, the repo's Playwright Chromium on SwiftShader). The scripts are in `/tmp/claude-0/-home-user-viral-engine/113885ae-d80b-5f3c-b080-dda23fa6260c/scratchpad/bench/` (`hand.mjs`, `fast.mjs`, `mc.mjs`, `rm.html` + `rm-run.mjs`). The test hand was a 9 cm palm+fingers made of 14 round cones (2 for the palm, 1 forearm stub, 3 fingers × 3 phalanges, a 2-segment thumb), with finger radii of 11–12.5 mm. The repo's glove is a similar size: palm sphere 0.06 scaled 0.88/0.82/0.55, finger radius about 0.016–0.0175.

## 1. SDF smooth union of capsules / round cones, polygonized per frame in JS

### Takeaway
This is the most controllable route and it fits the budget. Model each part with Inigo Quilez's exact round-cone / capsule SDFs and join them with the quadratic polynomial smooth-min, with a different blend radius per pair and a hard `min` between fingers. Then polygonize with naive surface nets on a grid fixed in palm space, with 2–3 mm cells (about finger radius ÷ 4–6). Normals come from the SDF gradient. In plain JS this costs about 40–100 ms of field evaluation per hand plus meshing, which is well inside a ~1 s/frame scene budget for a few hands. Webbing is avoided because the quadratic smin only bridges a gap narrower than 2k.

### Cited Findings
**Primitives (exact SDFs, GLSL; they port 1:1 to JS):**
- Capsule: `pa=p-a, ba=b-a; h=clamp(dot(pa,ba)/dot(ba,ba),0,1); return length(pa-ba*h)-r;`. The round cone `sdRoundCone(p,a,b,r1,r2)` between two points with two radii is exact and needs a single square root (`k=sign(rr)*rr*rr*x2; ...`). This is the right primitive for a tapered phalanx or forearm. `sdEllipsoid` is labelled "lower bound", not exact, so its distance shrinks or bends the blend width non-uniformly. Prefer round cones, or a palm made of 2 fat round cones — [iq, distance functions](https://iquilezles.org/articles/distfunctions/)
- iq labels Smooth Union / Subtraction / Intersection "bound, bound, bound": the result is no longer an exact distance, only a lower bound. His current code is `k*=4.0; h=max(k-abs(a-b),0.0); return min(a,b)-h*h*0.25/k;` — [iq, distance functions](https://iquilezles.org/articles/distfunctions/)

**Smooth-min choice and k:**
- iq normalizes every smin so that "k" is in distance units and "matches exactly the maximum inflation or thickening that the shapes a and b undergo". The normalized quadratic is `k*=4; h=max(k-abs(a-b),0)/k; return min(a,b)-h*h*k/4`. The cubic multiplies k by 6 and uses `h*h*h*k/6`. The quartic multiplies k by 16/3 and uses `h*h*h*(4-h)*k/16`. The circular variant multiplies k by `1/(1-sqrt(.5))` — [iq, smooth minimum](https://iquilezles.org/articles/smin/)
- Exponential, sigmoid and root smins "never return exactly neither a nor b", so the shapes "will be distorted everywhere in space". iq calls this "lack of Rigidity". The CD family (quadratic, cubic, quartic, circular) has no effect once the shapes are more than k apart. Use a CD-family smin so a fingertip far from the palm keeps its exact shape — [iq, smooth minimum](https://iquilezles.org/articles/smin/)
- All DD/CD smins underestimate distance in the blend region: the gradient length is below 1 there, so they never overshoot. Raymarching stays safe but is slower near blends. iq's circular-geometrical smin *overestimates* in convex areas and "vanilla raymarchers will fail" — [iq, smooth minimum](https://iquilezles.org/articles/smin/)
- The circular CD kernel is "the only one that leads to a CD smooth-minimum that produces an exactly circular connection between perpendicular objects". That makes it the cleanest fillet where a finger meets the palm at 90°. A quartic polynomial approximation exists for CPUs that want to avoid the sqrt — [iq, smooth minimum](https://iquilezles.org/articles/smin/)
- The blend factor for mixing materials (e.g. glove cuff colour vs palm) comes from the same smin: quadratic `h=1-min(abs(a-b)/(4k),1); w=h*h; m=w*.5; s=w*k; return a<b ? (a-s, m) : (b-s, 1-m)` — [iq, smooth minimum](https://iquilezles.org/articles/smin/)
- Media Molecule (Dreams) used the same quadratic soft-min, written unnormalized: `soft_min(a,b,r){ e=max(r-abs(a-b),0); return min(a,b)-e*e*0.25/r; }`, which "has no effect once abs(a-b) > r". Their culling has to account for "future soft blend", because soft blend widens each primitive's reach. They also store the compound SDF in 8³-brick volumes, each meshed independently with marching cubes — [Alex Evans, SIGGRAPH 2015 "Learning from Failure"](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf)

**Polygonizers available in JS:**
- three.js `MarchingCubes` addon: `new MarchingCubes(resolution, material, enableUvs, enableColors, maxPolyCount=10000)`. The field is a `Float32Array(resolution³)` in a [-1,1] cube, and `addBall` adds `strength/(1e-6+r²)-subtract`, i.e. inverse-square metaballs, not SDFs. Default `isolation=80`. Normals are central differences of the grid (`field[q-1]-field[q+1]`). `update()` rescans the whole grid every call. Buffers are fixed and overflow only warns. The bounding sphere is fixed at radius 1. The outer grid layer is never polygonized — [three.js MarchingCubes.js source](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/objects/MarchingCubes.js). You can write `field` yourself (e.g. `-sdf` scaled, with isolation 0) instead of using `addBall`. The official example runs at resolution 28 with a slider for 14–100 — [three.js webgl_marchingcubes.html](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webgl_marchingcubes.html)
- Naive surface nets (one vertex per sign-changing cell at the centroid of its edge crossings, quads across sign-changing edges): on a 65³ test volume it ran at 24 ms vs MC 30 ms (simple field) and 124 ms vs MC 275 ms (complex field). It made about 4× fewer vertices than MC (3,816 vs 15,268 in one example). It "can create non-manifold vertices" and has a bevelled look; dual contouring keeps sharp features. Mikola Lysenko's code: `surface-nets` (ndarray input, "any dimension") and `isosurface` (MC/MT/SN) — [0fps, Smooth voxel terrain part 2](https://0fps.net/2012/07/12/smooth-voxel-terrain-part-2/); [surface-nets README](https://github.com/mikolalysenko/surface-nets); npm `surface-nets` 1.0.2 and `isosurface` 1.0.0, last published 2022 — [npm registry](https://registry.npmjs.org/surface-nets), [npm registry](https://registry.npmjs.org/isosurface)
- Dreams' notes on SDF polygonization: "Marching cubes: Well it works but the meshes are dense and the edges are mushy and there are slivers". Dual contouring is "hard to keep sharp edges sharp and smooth things smooth"; manifold DC was "self intersecting again" — [Evans 2015](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf). For an all-smooth cartoon hand there are no sharp features, so DC's advantage doesn't apply.
- `manifold-3d` (WASM, v3.5.4, updated Sept 2026) has `Manifold.levelSet(sdf:(p)=>number, bounds, edgeLength, level?, tolerance?)`. It uses "a form of Marching Tetrahedra … on a body-centered cubic grid", sign convention "Positive values are inside". `tolerance>0` refines vertices onto the true surface at the cost of extra SDF calls. The output is guaranteed manifold — [manifold-3d type definitions](https://unpkg.com/manifold-3d@3.5.4/manifold-encapsulated-types.d.ts), [npm](https://registry.npmjs.org/manifold-3d). The SDF callback crosses the JS→WASM boundary once per sample.
- Normals: iq's tetrahedron gradient uses 4 SDF evaluations instead of 6 for central differences, with no directional bias: `normalize(k.xyy*f(p+k.xyy*h)+k.yyx*f(p+k.yyx*h)+k.yxy*f(p+k.yxy*h)+k.xxx*f(p+k.xxx*h))`, `k=(1,-1)` — [iq, normals for an SDF](https://iquilezles.org/articles/normalsSDF/). The quadratic smin also has an analytic gradient, `mix(∇a,∇b,h)` with `h=max(k-|a-b|,0)/(2k)` after the ×4 normalization — [iq, smooth minimum](https://iquilezles.org/articles/smin/)

**Local benchmarks (plain JS, Node 22, single thread; test hand above):**
- Naive surface nets with full-grid field evaluation, one Newton projection per vertex and tetrahedral-gradient normals (`hand.mjs`): 4 mm cells → 4.8k verts / 9.5k tris, 129 ms. 3 mm → 8.6k / 17k tris, 256 ms. 2 mm → 19k / 38k tris, 789 ms. 1.5 mm → 35k / 69k tris, 1.8 s. With a narrow band that skips 4³ blocks whose centre distance exceeds the block's half-diagonal (safe because the field is a lower bound): 86 / 100 / 364 / 596 ms. This version is unoptimized: it allocates an array in every SDF call and scans the full grid twice.
- Optimized field pass only (`fast.mjs`: no allocation, 8³ blocks, each finger group culled by its bounding sphere plus the blend radius, grid limited to hand + 5 cm of wrist): 3 mm (51×68×48) → 78k SDF evals, 42 ms. 2 mm → 181k evals, 93 ms. 1.5 mm → 333k evals, 159 ms. 1 mm → 774k evals, 446 ms. That is about 0.5 µs per evaluation for a 14-primitive hand. The surface crosses about 5k, 11k, 20k and 45k cells respectively.
- three.js `MarchingCubes.update()` with 12 `addBall`s, polygonization plus field (`mc.mjs`): resolution 48 → 20 ms (4.5k tris). 64 → 28 ms (7.9k tris). 96 → 51 ms (18k tris). 128 → 148 ms (32k tris). The addon's grid spans its own [-1,1] box, so a hand needs `res≈64–96` for a 2–3 mm cell on a ~15–20 cm box.

### Inferences
- **Blend radii per pair, not one global k** (these are derived from the normalized quadratic formula above). Two parallel fingers with a gap g give, at the midpoint, `smin = g/2 − k`. The surface therefore bridges (webbing) exactly when **g < 2k**, and the blend acts wherever |a−b| < 4k. Recommended structure:
  - `palm = smin(palmA, palmB, k≈0.6–0.8·r_finger)`
  - `palm = smin(palm, forearm, k≈0.8·r_finger)` (wrist fillet)
  - each finger: `F_i = smin(phalanx1, phalanx2, phalanx3; k≈0.15·r)`. This only softens the inner crease at a bent knuckle, because chained round cones sharing an end sphere are already smooth on the outside.
  - `d = min_i( smin(palm, F_i, k≈0.5·r_finger) )`, hard `min` *between* fingers.
  
  Each finger then fillets into the palm, but fingers never melt into each other. A crease remains only where two fingers' palm fillets meet near the knuckle line, and that is hidden if the finger bases are at least 2k apart. The test hand used k = 8/10/2/6 mm with r ≈ 12 mm.
- smin is not associative, so the result depends on nesting order. Fix the evaluation order in code (palm first, then each finger against palm) so the shape is deterministic and doesn't change when a finger moves in a list. This matters for the repo's "same storyboard → same video" rule.
- Use the 1-cell sign-only trick from the benchmark (write ±1 into far blocks). Surface nets/MC only need the sign away from the surface, and that is what makes 2 mm affordable.
- Surface nets fits best for the mesh path: it produces quad-dominant meshes with fewer, better-shaped faces than MC, it is trivially written in about 80 lines of JS, and one Newton step (`p -= ∇f·f`) puts vertices on the true surface, which removes most of the "bevelled" look. three's addon is quick to try but is built around metaballs, a fixed [-1,1] box and a fixed polygon budget, so it adds little.
- Budget: at 2–3 mm cells a hand costs roughly 50–150 ms of CPU in JS for field plus mesh, before rendering. A few hands per frame fits a ~1 s/frame budget, and the repo already spends about 1.7 s/frame in SwiftShader drawing (CLAUDE.md "Keeping it fast and cheap").
- Memory is small: a 76×101×71 Float32 field (2 mm) is 2.2 MB; 1 mm is about 17 MB. Reuse the typed arrays and the BufferGeometry (preallocate, `setDrawRange`, `needsUpdate`) instead of reallocating each frame.

### Gaps
- No published timings were found for surface nets or MC on a hand-sized SDF in JS. The numbers above are this session's own micro-benchmarks, and the meshing pass after the optimized field pass was not timed separately. The unoptimized full pipeline suggests about +50–250 ms at 2 mm, and an optimized one should be well under that.
- `manifold-3d` `levelSet` speed for a JS callback SDF was not measured.

## 2. Raymarching the SDF in a fragment shader instead

### Takeaway
Raymarching gives a perfect, resolution-independent blended surface with exact per-pixel normals and no popping. The costs come from SwiftShader: about 1.2–1.4 µs per covered pixel was measured on 4 cores, so a 300 px hand costs about 0.1 s and a 600 px hand about 0.5 s. That is before an outline or shadow pass, which runs the march again. You also have to write `gl_FragDepth` yourself, build custom shadow and outline handling, and lose `OutlineEffect`. It is viable for close-ups of one hand, but the polygonized mesh is cheaper and fits the existing pipeline.

### Cited Findings
- The standard way to put a raymarched SDF into a three.js scene: draw a proxy box or quad, march in its fragment shader, and write `gl_FragDepth` from the hit point so it depth-sorts with ordinary meshes. Forum threads show people struggling with the depth formula. One fix was to transform the camera position into the proxy's local space (`cube.worldToLocal(camPos)`) — [three.js forum: intersect raymarched object with mesh](https://discourse.threejs.org/t/can-we-intersect-fragment-raymarched-object-with-regular-mesh/59922); [three.js forum: correct gl_FragDepth](https://discourse.threejs.org/t/raymarching-correct-gl-fragdepth/66033); [three.js forum: SDF in a three.js scene](https://discourse.threejs.org/t/how-do-you-integrate-signed-distance-fields-sdf-into-a-basic-three-js-scene/77504)
- Smooth-min blend regions underestimate distance (gradient < 1), so sphere tracing slows near blends but stays correct. Dreams notes that "edge pixels are waaaay harder than surface" pixels for sphere tracing — [iq, smooth minimum](https://iquilezles.org/articles/smin/); [Evans 2015](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf)
- Dreams' shipped "brick engine" rasterized 8³ bounding cubes and raymarched only inside each, outputting depth ("POM/tiny raymarch inside each 8x8x8 cube … with odepth to set the zbuffer"). This bounded-proxy trick keeps march lengths short — [Evans 2015](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf)
- WebGL shader compilers can choke when a long `map()` is inlined 4–6 times for normals. iq documents the `#define ZERO (min(iFrame,0))` loop trick to stop the inlining, and notes it "often happens in WebGL" — [iq, normals for an SDF](https://iquilezles.org/articles/normalsSDF/)
- **Local benchmark** (`rm.html`): a WebGL2 full-screen 1080×1920 canvas under the repo's SwiftShader flags. The test hand was the same 14 round cones with smin, a bounding-sphere ray start, 64 max steps, a tetrahedral normal and a toon step. A 300×300 px region took 111 ms per draw, 600×600 took 497 ms, 1080×1080 took 1,475 ms, and 600×600 with 128 steps took 557 ms. That is about 1.2–1.4 µs per pixel.

### Inferences
- Under SwiftShader the cost scales with screen coverage × steps × primitives, and every extra pass repeats it: a shadow caster's `customDepthMaterial` would have to raymarch too, and an outline post-pass or a second march for ink adds more. A mesh is rasterized almost for free once built. For 2–4 hands at about 200–400 px each in a 1080×1920 frame, raymarching would add about 0.2–1 s per frame, the same order as the whole current budget.
- Outlines with raymarching: silhouette ink is cheap (track the minimum `d` along a missing ray and ink when `min d < w·t`). Inner contours, such as a curled finger in front of the palm, need a depth- or normal-discontinuity test or a second ray. Neither matches `OutlineEffect`'s look exactly, so the hand ink would differ from the body ink.
- Raymarching stays a good *reference* renderer for checking the mesh path (a pixel-diff A/B, per the repo's rule 12) and for a single hero close-up.

### Gaps
- `gl.getParameter(gl.RENDERER)` returned the masked string "WebKit WebGL", so the benchmark didn't confirm the backend was SwiftShader. It was launched with the repo's SwiftShader flags and no GPU is present. No published SwiftShader raymarching benchmarks were found.

## 3. Metaballs / convolution surfaces vs SDF smooth-min

### Takeaway
Classic metaballs (three's `addBall`, inverse-square fields) and convolution surfaces blend globally. Every primitive's field adds up, so nearby fingers swell and bridge, and radii are hard to control. SDF primitives with clamped (CD-family) smin keep exact radii away from joins and allow per-pair blend widths. For a hand with close-together fingers, SDF + smin is the better fit. Convolution surfaces along line segments are the closest classical equivalent and are bulge-free only under conditions.

### Cited Findings
- three's metaball field is `strength/(1e-6+r²) − subtract`, summed over balls and thresholded at `isolation` (default 80). The surface position depends on the sum of all nearby contributions, not on one primitive's radius — [three.js MarchingCubes.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/objects/MarchingCubes.js)
- Convolution surfaces (Bloomenthal & Shoemake, SIGGRAPH 1991) convolve skeletal primitives (segments, polygons) with a 3D Gaussian kernel. This removes the bulges and curvature discontinuities that summed distance-based fields get where several primitives contribute — [SIGGRAPH history record](https://history.siggraph.org/?p=120593); [McCormack & Sherstyuk, "Creating and rendering convolution surfaces"](https://users.monash.edu/~jonmc/research/Papers/CONVOLUT.PDF)
- Bloomenthal's 1997 follow-up found branching skeletons are bulge-free only "if skeletal elements are sufficiently large with respect to the convolution kernel". Analytic line-segment convolution assumes uniform weights, giving constant-radius tubes, unless polynomial weight distributions are used (Jin et al.) — [Convolution surfaces for line skeletons with polynomial weight distributions](https://typeset.io/pdf/convolution-surfaces-for-line-skeletons-with-polynomial-56pupsgtrx.pdf); [Bloomenthal SIGGRAPH 2003 course notes](https://unchainedgeometry.com/papers/sig03tut.pdf)
- A Dreams prototype emulated soft blends offline with "3DS Max's blob mode". The shipped tool kept "lists of simple SDF elements" with soft min/max as "the opposite of a failure" — [Evans 2015](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf)

### Inferences
- With summed fields every finger's field reaches every other finger, so a 3-finger mitten webs or fattens as fingers close, unless the field falloff is tuned so short that joins become creased. A per-pair clamped smin gives "blend here, not there" directly.
- Convolution surfaces could make a lovely tapered tube, but variable radius needs non-trivial kernels and they are still summed fields. There is no advantage over round-cone SDFs for this use.

### Gaps
- No JS library for convolution surfaces was found, and none was looked for in depth.

## 4. One procedurally generated skinned mesh (B-Mesh / Skin modifier / sphere-meshes) + LBS/DQS

### Takeaway
This is the other serious option: build one quad-dominant branching-tube mesh around a skeleton of balls (B-Mesh, which is Blender's Skin modifier), or polygonize the SDF *once* in the rest pose. Then bind it to bones and let three.js `SkinnedMesh` deform it every frame on the GPU (here, SwiftShader's vertex stage, which is cheap). The topology stays fixed, so nothing can pop. The cost moves to fixing skinning artifacts (knuckle collapse, candy-wrapper twist at the wrist), since three.js has only linear blend skinning built in.

### Cited Findings
- B-Mesh (Ji, Liu, Wang, CGF 29(7) 2010): the user draws a 1-D skeleton with "key balls" at the nodes. The system builds a quad-dominant initial mesh, then subdivides and evolves it into a quad mesh "with good edge flow along the skeleton", aimed at sculpting and skeleton-based animation — [Eurographics digital library](https://diglib.eg.org/handle/10.2312/CGF.v29i7pp2169-2177). There is an open-source implementation (Qt/OpenGL) at [CorentinDumery/BMesh](https://github.com/CorentinDumery/BMesh).
- Blender's Skin modifier is based on B-Mesh. It uses per-vertex radii on vertices and edges, outputs "mostly quads, although some triangles will appear around intersections", and has "Branch Smoothing" that "relaxes the surface around these points, with the side effect of shrinking it". Branch vertices otherwise "generate extra edge loops along adjacent edges in order to keep the output tight". "Create Armature" makes one bone per edge, adds weight groups and puts the Armature modifier after the Skin modifier "because it should only deform the output". It is normally followed by Subdivision Surface — [Blender manual, Skin modifier](https://docs.blender.org/manual/en/latest/modeling/modifiers/generate/skin.html)
- The Blender commit that introduced it notes it lacks B-Mesh's mesh evolution and fairing steps — [Blender git log](https://miikahweb.com/fi/blender/git-logs/commit/8801330c18b063e341e8263131c91695cd1b7bdf) (as summarised in search results; not opened directly).
- Sphere-meshes (Thiery, Guy, Boubekeur, SIGGRAPH Asia 2013) replace point interpolation with sphere interpolation, where each edge is the convex hull of two spheres (a tapered capsule). They are fitted with a "Spherical Quadric Error Metric", and a header-only C++ SQEM is available. A sphere-mesh hierarchy can serve as a rig — [paper PDF](https://www.telecom-paristech.fr/~boubek/papers/SphereMeshes/SphereMeshes.pdf); [SQEM code](https://www.github.com/superboubek/SQEM). Tkach, Pauly & Tagliasacchi (SIGGRAPH Asia 2016) used sphere-meshes as a real-time hand model for tracking at 60 Hz — [EPFL record](https://infoscience.epfl.ch/record/225097); [hmodel code](https://github.com/OpenGP/hmodel)
- three.js `SkinnedMesh` needs a `Skeleton` plus `skinIndex`/`skinWeight` buffer attributes (up to 4 influences) and uses linear blend skinning. No dual-quaternion option was found — [three.js SkinnedMesh docs](https://threejs.org/docs/pages/SkinnedMesh.html). Matrix-blend skinning "pinch[es]" toward the joint, the candy-wrapper effect — [Urho3D forum](https://urho3d-forum-archive.github.io/t/dual-quaternion-skinning/42). Dual quaternion skinning (Kavan et al., I3D 2007) "solves the artifacts of linear blend skinning at minimal additional cost" — [CTU publication page](https://dcgi.fel.cvut.cz/en/publications/2007/kavan-i3d-sdq/). Disney notes DQS is not a pure drop-in for LBS in production and adds fixes for bulging — [Disney Animation, Enhanced DQS](https://www.disneyanimation.com/publications/enhanced-dual-quaternion-skinning-for-production-use/)

### Inferences
- **A hybrid fits this repo best:** polygonize the smin-SDF hand once per hand design (or per costume) in its rest pose with the method from section 1, at fine resolution (1–1.5 mm) and offline-quality cost. Compute skin weights from the same SDF: weight per bone ∝ the falloff of that bone's primitive distance, or take iq's smin mix factor at each vertex. Then animate with `SkinnedMesh`. This gives the seamless blended look, fixed topology (no popping, stable outlines), and an almost-free per-frame cost.
- The weak spots of that hybrid are finger curl and the palm fillet. A curled finger's fillet should change shape (the SDF route recomputes it, skinning only bends it), and LBS loses volume on the inside of a 90° knuckle. Mitigations: 2–3 bones per finger with soft weights across each joint, corrective morph targets for the full curl (three supports morph + skin together), or a custom DQS vertex shader via `onBeforeCompile`, which is doable but not built in.
- B-Mesh-style sweeping by hand in JS is more code (convex-hull stitching at the palm branch node, then subdivision) than SDF + surface nets. The Skin modifier's own docs admit branch points get "complicated topology, some of which may overlap", and the hand's palm is exactly a 4–5-way branch.

### Gaps
- No JS/npm implementation of B-Mesh or the Skin modifier was found (only Qt/C++ and Blender's C code).
- The sphere-mesh hand model's exact sphere count and rendering method could not be read: the EPFL/lgg PDF URLs returned HTML or 202 to curl.

## 5. Outlines (inverted hull vs post-process) on blended vs separate primitives

### Takeaway
On separate interpenetrating primitives, each part's inverted hull pokes out a thickness-wide band around every intersection curve. You see this as ink rings where a finger enters the palm or at each knuckle ball: the "stuck-on" look. A post-process normal or depth edge filter also fires there, because the normal jumps at the crease. One closed blended surface with continuous normals has no intersection curves, so the hull or edge filter draws ink only at real silhouettes and folds (a curled finger over the palm), which is what's wanted.

### Cited Findings
- The repo's ink is three's `OutlineEffect`. It re-renders each mesh with `side: BackSide` and moves each vertex along its normal in clip space: `pos + normalize(pos - pos2) * thickness * pos.w`, with thickness 0.0042 by default and per-material `userData.outlineParameters` — `node_modules/three/examples/jsm/effects/OutlineEffect.js` lines 82–108; `engine/page/styles.js` lines 30–46 (local source).
- The inverted hull technique is an enlarged, inverted, black copy of the mesh that shows only past the silhouette (credited to Jet Set Radio) — [Inverted Hull Outlines notes](https://noggi3d.notion.site/Line-Art-36a2ccea40b18002a370ca9655169cd0). Artists report that "close or intersecting vertices, or separate pieces on top of each other" make the outline "look like it's exploding" — [Polycount thread](https://polycount.com/discussion/comment/2732547/)
- Inside/outside logic needs a well-behaved, closed mesh where each edge is shared by exactly two faces — [POV-Ray news thread](https://news.povray.org/povray.unofficial.patches/thread/%3C39ad16ac%40news.povray.org%3E). libigl's `outer_hull` expects intersections to be resolved first — [libigl outer_hull.h](https://git.inf-cv.uni-jena.de/3DFaces/libigl_Martin/src/068618046e0a6437f620763985af0197bb6940b8/include/igl/outer_hull.h)

### Inferences
- Why separate primitives draw internal lines: where primitive A enters primitive B, A's back-face shell is pushed outward along A's normals. Right along the intersection curve, A's surface is level with B's, so the pushed-out shell sits up to `thickness` *in front of* B's front faces and is not covered. The result is a ring roughly as thick as the outline (about 4 px here, since 0.0042 in NDC × 960 px half-height is about 4 px) around every junction. The repo's knuckle balls each add more junction rings. Hiding them (e.g. `noOutline` on the inner parts) also removes the parts' real silhouettes.
- On a blended mesh the shell is one closed offset of one surface, so ink appears only where the surface turns away from the camera. For this to hold, normals must be smooth across the fillet. Use SDF-gradient (or averaged) vertex normals, not faceted ones: OutlineEffect extrudes along the vertex normal, and split normals tear the shell open.
- Hull artifact to watch: in tight concavities narrower than the line width on screen (between fingers, inside a fist), the back-face shell can poke through the front surface. Keep the finger gap ≥ 2k in world units and check fists in close-up. The hard `min` crease between touching fingers is a real fold and should get a line.
- A post-process Sobel on normals/depth has the same rule: no normal discontinuity, no line. Its threshold must sit above the curvature change across a k-wide fillet. At about 2–4 px across the fillet on screen that is easy, but it must be checked at the wrist fillet, which is the widest.

### Gaps
- No authoritative article was found that specifically documents inverted-hull rings at mesh intersections. The mechanism above is derived from the OutlineEffect shader code and the general reports; it should be confirmed with a still of the current glove hand.

## 6. Temporal stability, performance and memory in practice

### Takeaway
To keep a per-frame polygonized hand from shimmering, put the grid in the palm's local frame with a fixed origin and cell size, set the cell to no more than about r_finger/5, project vertices onto the true surface, take normals from the analytic or tetrahedral SDF gradient rather than from triangles, and keep the evaluation order and blend radii constant. Even then, the triangles change as fingers slide across the grid, which can twitch the outline by a pixel. If that shows in a 15 fps strip, switch to the "polygonize once + skin" hybrid from section 4.

### Cited Findings
- Media Molecule moved away from per-edit marching-cubes meshes partly over quality ("dense … mushy … slivers") and LOD. Their final approach spawns points only in 2×2×2 neighbourhoods with a zero crossing ("dual grid") — [Evans 2015](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf)
- Soft min must "revert to hard min/max once distance fields are sufficiently far apart (otherwise you can never cull either side)". Culling must also include the blend reach — [Evans 2015](https://advances.realtimerendering.com/s2015/AlexEvans_SIGGRAPH-2015-sml.pdf)
- three's MarchingCubes recomputes the full grid each `update()`, its buffers overflow silently past `maxPolyCount` (only a console warning), and the bounding sphere is fixed at radius 1, so frustum culling can be wrong for a scaled hand — [three.js MarchingCubes.js](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/objects/MarchingCubes.js)
- The repo's renders must be deterministic (no `Math.random`, no wall clock), and full renders cost about 1.7 s/frame in SwiftShader — `CLAUDE.md` (local).

### Inferences
- **Grid anchoring:** anchor to the palm bone, not the world, so a moving arm doesn't slide the surface through the grid. Only finger motion relative to the palm changes the sampling. Snapping the grid origin to multiples of h in palm space keeps two frames with the same pose bit-identical.
- **Vertex placement:** naive centroid placement aliases to the grid, so curl-driven motion makes vertices crawl. One Newton step (`p -= n·f(p)`, 4 extra SDF evals with the tetrahedral gradient) puts every vertex on the analytic surface, so the silhouette moves continuously even as the triangulation changes. This was used in `hand.mjs`.
- **Shading:** toon shading thresholds `dot(n,l)`, so a faceted normal gives a jagged, flickering terminator. SDF-gradient normals per vertex keep the terminator smooth. For an even better band, the vertex normal can be overridden per fragment only if the SDF were in the shader, which it is not on the mesh path.
- **Resolution rule of thumb:** h ≈ r_min/5, where r_min is the thinnest fingertip radius. That is about 2–3 mm for the 11–17 mm finger radii here, giving 9k–38k triangles per hand, comfortable for SwiftShader rasterization. Below about r/3 the tips turn faceted and can drop thin features.
- **Cost summary (local, JS single thread):** field 40–95 ms at 3–2 mm with block culling, plus meshing tens to a few hundred ms depending on implementation quality. three's MC at res 64–96 is 28–51 ms for metaballs. Raymarching under SwiftShader is about 0.11 s per 300 px hand and 0.5 s per 600 px hand, per pass. The skinned-hybrid per-frame cost is about the same as today's separate primitives.
- **Memory:** about 2–17 MB of Float32 field per hand at 2–1 mm, plus an Int32 vertex-index grid of the same element count. Reuse them across frames. A Web Worker could polygonize hands in parallel with the main thread (4 cores here), but this was not tested.
- **Recommended order to try:** (1) build the SDF hand with the per-pair smin structure; (2) render it as surface nets per frame at 2.5 mm and look at a 15 fps strip of a curl for shimmer; (3) if it shimmers, or for speed, bake the rest pose once and skin it. In both cases the OutlineEffect internal rings at the junctions disappear.

### Gaps
- Frame-to-frame shimmer of the surface-nets hand was not measured on rendered frames in this session (only timings). A pixel-diff of consecutive frames at constant pose vs a slowly curling finger would settle it.
- Worker/WASM speed-ups for the field pass were not benchmarked.
